# 墨水屏色板标定（SE0398NZ07，A0 面板）

更新：2026-10-31

## 结论：面板是 黑 / 白 / 黄 / 红（BWRY），不是黑 / 白 / 红 / 蓝

- 驱动里 2bpp 码与颜料的对应（社区驱动 `epd3in98.py` + 实板验证）：
  `0=黑 1=白 2=黄 3=红`
- 实拍证据：
  - `docs/微信图片_20261031015323_58_2.jpg`（行映射标定页，黑白）
  - `docs/微信图片_20261031020115_59_2.jpg`（四角色块：上角暗红、下角橙黄）
- 这块面板**没有蓝色颜料**。蓝色/青色内容在四色屏上只能退化成灰、褐或黄，
  这是物理限制（也是「照片偏色」最常见的原因），不是驱动映射错。

## 色板采样（2026-10-31）

方法：对 `docs/微信图片_20261031020115_59_2.jpg` 取各色块内部区域的中位数，
再除以**同一张照片里、同一光照下的纸白**做归一化（抵消曝光与白平衡），
最后乘回纸白假设值 `204,204,198`。

| 颜料 | 照片内中位数 | 局部纸白 | 归一化比值 | 标定后 sRGB |
|------|--------------|----------|------------|-------------|
| 黑   | 28,26,26     | —        | ≈0.16/0.16/0.17 | 33,32,34 |
| 白   | —            | —        | 1.00       | 204,204,198（假设值） |
| 黄   | 191,113,7    | 170,162,149 | 1.12/0.70/0.05 | 217,133,9 |
| 红   | 92,25,17     | 173,164,151 | 0.53/0.15/0.11 | 109,31,22 |

要点：**这块屏的「黄」明显偏橙**（相对纸白绿通道只有 ~0.65、蓝几乎为 0）。
旧色板按浅黄 `222,190,74` 建模，量化时会多撒黄点、少撒白点，
结果整幅偏暖偏暗（实测平均误差 51.3 → 标定后 45.4，通道偏置 R−22/G−27/B−27 → R−10/G−17/B−20）。

## 重新标定的方法

1. 让屏幕显示纯色块（`epd_hello` 或临时测试页），手机正对拍摄，画面里保留大片纸白
2. 取每个色块内部区域的中位数，再除以附近的纸白中位数
3. 比值 × `(204,204,198)` 写回上表三处
4. 用 `python tools/epd_preview.py 图片.jpg` 对比效果，再上板确认

局限：手机拍照有自动白平衡/对比度/饱和度处理，绝对值和彩度都可能被夸大，
所以数值以「相对纸白」为准；一次标定后如需微调，改三处常量即可。

|------|------------|----------------|---------|---------|

| 白   | 150,131,156| 1.00           | 204,204,198（假设值） | 同左 |
| 黄   | 159,99,73  | 1.06/0.76/0.47 | **216,154,93** | 217,133,9 |
| 红   | 89,43,62   | 0.59/0.33/0.40 | **121,67,79** | 109,31,22 |

用户目视确认这张照片的颜色与实屏一致，故按它重标定三处常量
（`image_pipeline.c` / 网页 `PAL` / `epd_preview.py`），并重新生成
`pal_lut.h`（`python tools/gen_pal_lut.py`）。

要点：实测颜料比早先估计**更浅、更不饱和** —— 黑相对纸白 0.27（旧模型 0.16），
黄偏土黄（蓝 0.47）、红偏玫红（绿 0.33 / 蓝 0.40）。

副作用与处理：
- 色板点变近后，网页（float32 缓冲）与 numpy（float64）在色域映射边界上的
  舍入差异被误差扩散放大，逐像素一致率从 99.8% 掉到 86%；
  把 `index.html` 的 L/A/B 与扩散缓冲改成 `Float64Array` 后回到 **100%**
- 旧的 `docs/微信图片_20261031020115_59_2.jpg` 标定（白天、更干净）与这次
  差异主要在蓝通道，判断为拍摄光照/相机白平衡差异；以用户认可的这次为准

局限仍然成立：一次拍照受相机色调曲线影响，绝对亮度不可信；如需再调，
重复「刷色卡 → 白天正对拍照 → `check_color_card.py`」即可。

## 修正（2026-11-02）：弃用夜间粉光照片的标定，改回白天实测

用户反馈「颜色很大问题」后复核发现：2026-10-31 深夜那张色卡照片是在**粉色补光**
下拍的，纸白实测 (150,131,156)（蓝比绿高 = 明显偏粉），相机又把暗部整体抬高。
用它做「相对纸白」归一化，会得到：

- 黑 0.27（真实约 0.16）→ 黑色颜料被建模成中灰，暗部发灰
- 黄 1.06/0.76/**0.47**（白天照片 1.13/0.74/**0.05**）→ 黄色被建模成浅土黄，
  量化器会把中性亮区判给黄，实屏却是金黄点 → 整幅橙褐
- 红 0.59/**0.33/0.40**（白天 0.58/**0.18/0.13**）→ 红被建模成玫红

同一块屏在白天的照片 `docs/微信图片_20261031020115_59_2.jpg` 中取样
（四角红/黄色块 + 白纸 + 黑条中位数，归一化到同一张照片的纸白）：

| 颜料 | 白天照片中位数 | 相对纸白 | ×(204,204,198) |
|------|----------------|----------|----------------|
| 黑（竖条） | 26,26,27 | 0.16/0.16/0.18 | **32,33,35** |
| 白（纸面） | 167,160,151 | 1.00 | 204,204,198（假设值） |
| 黄（角块亮侧） | 189,119,8 | 1.13/0.74/0.05 | **231,152,10** |
| 红（角块） | 96,28,20 | 0.58/0.18/0.13 | **117,36,26** |

更新的三处常量：`image_pipeline.c` / 网页 `PAL` / `epd_preview.py`，并重新生成
`pal_lut.h`。网页与 numpy 逐字节一致率回到 100%（grain 1/2/3）。

教训：**拍照标定只信白天自然光**；夜间混合光/补光会让彩度整体失真，尤其蓝通道。
如果再标定，先看照片里「纸白」的三通道是否接近相等，偏差大就直接重拍。

## 以出厂演示图为参照标定「渲染强度」（2026-11-03）

色板（颜料本身的 sRGB）已经由色卡照片定死；这一轮改的是**把照片送进四色
空间之前要乘多少**——也就是默认曝光/颗粒。参照物是面板出厂默认显示的样片
照片 `docs/微信图片_20261103001052_1_45.jpg`。

做法：把照片做透视校正，再用照片里的白（(255,233,221)）与黑（(118,71,62)）
反解出相机在**线性域**的逐通道增益和眩光，得到 768×552 的「面板空间」目标图；
然后把我们的渲染结果用同一个相机模型投回去，比较 Oklab 平均色差。

结论：

- 面板白 204 在线性域是 0.604。普通手机照片的白是 255（线性 1.0），
  正确的做法是**乘 0.60** 把它压回面板范围；乘 1.35 会把中间调全部顶到
  纯白，量化后就是「发白、发土、白点太多」。
- 出厂图是**单像素抖动**（1× 颗粒），不是成团抖动。
- 数值：曝光 0.60 / gamma 1.00 / 对比度 1.05 / 饱和 1.15 / 颗粒 1×。
  在这个设置下与出厂图的平均色差比旧默认值小 3 倍以上（0.024 vs 0.081）。

**不要用这张出厂图反推色板**：它里面没有大面积纯黄/纯红，抖动点又被镜头和
JPEG 糊成混色，反解只会得到偏白、偏土的假色板——和 10-31 夜间照片踩过的坑
是同一个。色板只认「大面积纯色块」的照片（色卡）。
