# 墨水屏色板标定（SE0398NZ07，A0 面板）

更新：2026-10-31

## 结论：面板是 黑 / 白 / 黄 / 红（BWRY），不是黑 / 白 / 红 / 蓝

- 驱动里 2bpp 码与颜料的对应（社区驱动 `epd3in98.py` + 实板验证）：
  `0=黑 1=白 2=黄 3=红`
- 实拍证据：
  - `docs/微信图片_20261031015323_58_2.jpg`（行映射标定页，黑白）
  - `docs/微信图片_20261031020115_59_2.jpg`（四角色块：上角暗红、下角橙黄）
- 这块面板**没有蓝色颜料**。蓝色/青色内容在四色屏上只能退化成灰、褐或黄，
  这是物理限制（也是「照片偏色」最常见的原因），不是驱动映射错。

## 色板采样（2026-10-31）

方法：对 `docs/微信图片_20261031020115_59_2.jpg` 取各色块内部区域的中位数，
再除以**同一张照片里、同一光照下的纸白**做归一化（抵消曝光与白平衡），
最后乘回纸白假设值 `204,204,198`。

| 颜料 | 照片内中位数 | 局部纸白 | 归一化比值 | 标定后 sRGB |
|------|--------------|----------|------------|-------------|
| 黑   | 28,26,26     | —        | ≈0.16/0.16/0.17 | 33,32,34 |
| 白   | —            | —        | 1.00       | 204,204,198（假设值） |
| 黄   | 191,113,7    | 170,162,149 | 1.12/0.70/0.05 | 217,133,9 |
| 红   | 92,25,17     | 173,164,151 | 0.53/0.15/0.11 | 109,31,22 |

要点：**这块屏的「黄」明显偏橙**（相对纸白绿通道只有 ~0.65、蓝几乎为 0）。
旧色板按浅黄 `222,190,74` 建模，量化时会多撒黄点、少撒白点，
结果整幅偏暖偏暗（实测平均误差 51.3 → 标定后 45.4，通道偏置 R−22/G−27/B−27 → R−10/G−17/B−20）。

## 重新标定的方法

1. 让屏幕显示纯色块（`epd_hello` 或临时测试页），手机正对拍摄，画面里保留大片纸白
2. 取每个色块内部区域的中位数，再除以附近的纸白中位数
3. 比值 × `(204,204,198)` 写回上表三处
4. 用 `python tools/epd_preview.py 图片.jpg` 对比效果，再上板确认

局限：手机拍照有自动白平衡/对比度/饱和度处理，绝对值和彩度都可能被夸大，
所以数值以「相对纸白」为准；一次标定后如需微调，改三处常量即可。

## 修正（2026-11-02）：弃用夜间粉光照片的标定，改回白天实测

用户反馈「颜色很大问题」后复核发现：2026-10-31 深夜那张色卡照片是在**粉色补光**
下拍的，纸白实测 (150,131,156)（蓝比绿高 = 明显偏粉），相机又把暗部整体抬高。
用它做「相对纸白」归一化，会得到：

- 黑 0.27（真实约 0.16）→ 黑色颜料被建模成中灰，暗部发灰
- 黄 1.06/0.76/**0.47**（白天照片 1.13/0.74/**0.05**）→ 黄色被建模成浅土黄，
  量化器会把中性亮区判给黄，实屏却是金黄点 → 整幅橙褐
- 红 0.59/**0.33/0.40**（白天 0.58/**0.18/0.13**）→ 红被建模成玫红

同一块屏在白天的照片 `docs/微信图片_20261031020115_59_2.jpg` 中取样
（四角红/黄色块 + 白纸 + 黑条中位数，归一化到同一张照片的纸白）：

| 黄（角块亮侧） | 189,119,8 | 1.13/0.74/0.05 | **231,152,10** |
| 红（角块） | 96,28,20 | 0.58/0.18/0.13 | **117,36,26** |

更新的三处常量：`image_pipeline.c` / 网页 `PAL` / `epd_preview.py`，并重新生成

## 以出厂演示图为参照标定「渲染强度」（2026-11-03）

色板（颜料本身的 sRGB）已经由色卡照片定死；这一轮改的是**把照片送进四色
空间之前要乘多少**——也就是默认曝光/颗粒。参照物是面板出厂默认显示的样片
照片 `docs/微信图片_20261103001052_1_45.jpg`。

做法：把照片做透视校正，再用照片里的白（(255,233,221)）与黑（(118,71,62)）
反解出相机在**线性域**的逐通道增益和眩光，得到 768×552 的「面板空间」目标图；
然后把我们的渲染结果用同一个相机模型投回去，比较 Oklab 平均色差。

结论：

- 面板白 204 在线性域是 0.604。普通手机照片的白是 255（线性 1.0），
  正确的做法是**乘 0.60** 把它压回面板范围；乘 1.35 会把中间调全部顶到
  纯白，量化后就是「发白、发土、白点太多」。
- 出厂图是**单像素抖动**（1× 颗粒），不是成团抖动。
- 数值：曝光 0.60 / gamma 1.00 / 对比度 1.05 / 饱和 1.15 / 颗粒 1×。
  在这个设置下与出厂图的平均色差比旧默认值小 3 倍以上（0.024 vs 0.081）。

**不要用这张出厂图反推色板**：它里面没有大面积纯黄/纯红，抖动点又被镜头和
JPEG 糊成混色，反解只会得到偏白、偏土的假色板——和 10-31 夜间照片踩过的坑
是同一个。色板只认「大面积纯色块」的照片（色卡）。

## 补充：曝光要跟着「这张图自己的白位」走（2026-11-03 晚）

上面那轮标定定的是「照片白 255 → 面板白 204 ⇒ 线性增益 0.60」。这没问题，
但它假设输入里真的有 255 的白。用户给的原图
`docs/微信图片_20261103011900_3_45.png` 最亮处只有 229（亮度 99.5 分位 229），
乘 0.60 等于整体压暗 27%，皮肤/红衣比出厂实拍暗 15–20%。

用出厂照片反解相机模型后比较同一材质：原图白 224、肤色 189/143/121；
面板空间白 204、肤色 180/141/115。两组的「肤色÷白」几乎相等
（0.844 vs 0.848），说明出厂就是**把白位线性映射到 204**，没有额外 S 曲线。

所以实现的是**自动白点**：按亮度 99.5 分位估白位 `w`，乘 `1/lin(w)`
（夹 1.0–2.4），再乘滑块曝光。滑块 0.60 的含义不变：
- 有真白的照片（高光到 255）增益 = 1，输出与之前逐字节相同
- 没有高光的图（如这张原图，增益 1.27）会被提亮，有效曝光 0.76

注意：这里没有改动色板，也没有再拿出厂图反推色板（原因见上一节）。

## 整张印刷色卡对照（2026-11-08）

用户给了印刷色卡原图 `docs/色卡-raw.jpg`（1080×869，6 行 50 块）和色卡显示在
面板上的照片 `docs/色卡-显示.jpg`，要求「对比色彩差异再调整」。

做法：把原图按面板的 cover 裁切（768×552，上下各切掉 46 px）当输入，跑完整
管线（自动白点 1.08×、0.60/1.00/1.05/1.15、颗粒 1×、凸包投影 + FS 抖动），
再对 41 块**完全可见**的色块取抖动后的块平均，和原色比 Oklab。

度量口径很重要：四色屏的中/间调是靠两色像素混出来的，眼睛看到的是**块平均**，
不是投影点。同一张渲染，按投影点算平均 ΔE00 是 0.148，按抖动后块平均算是
0.175——差出来的 0.03 全是误差夹紧（±0.25）带来的系统性偏暗，只看投影点会
把问题算小。

结果（`evidence/M2/colorcheck/patches_report.txt`、`card_compare.png`）：

| 指标 | 值 |
|------|----|
| 平均 ΔE00 | 0.175 |
| 最差 6 块 | 草绿 0.312、淡绿 0.304、紫罗兰 0.271、钴蓝 0.254、黑色 0.248、群青 0.245 |

差的全部是**这块屏印不出来的色**：绿（没有绿墨，最近边永远是黄-黑 ⇒ 橙）、
蓝紫（最近边是黑-白 ⇒ 灰）、纯黑（面板黑 32,33,35）。红/黄/橙/肤色/中性灰
的 ΔE00 都在 0.06~0.20，属于色板本身能解释的范围。

因此这一轮**不改默认参数**，理由都测过：

1. **曝光**：只扫曝光时，色卡在「有效曝光 ≈ 0.95」处 ΔE00 最低（0.1475，
   当前有效 0.65 是 0.168）。但那是让高光全部削到面板白换来的——出厂图的
   反解（见上一节）明确显示面板就是「白位线性映射到 204」，不削高光。色卡
   一半以上是中间调，这个指标天然偏好削高光，不能拿来定曝光。
2. **gamma**：gamma 1.15~1.20 能把色卡 ΔE00 压到 0.150，效果和抬曝光同源
   （都是抬中间调），同样会被出厂结论否掉。
3. **绿色保护**：对「目标是绿-青、最近点色相偏 >45°」的像素改投中性灰轴
   （保亮度、丢色度）。三种阈值都试了，41 块平均 ΔE00：基线 0.1746 /
   75°,45° 0.1742 / 110°,45° 0.1747 / 110°,30° 0.1798。**收益在噪声里**，
   而视觉上会把草绿、黄绿这一整行变成接近纸白的灰点，和相邻橙色块割裂，
   比统一偏橙更难看。放弃，脚本留在 `evidence/M2/colorcheck/guard_eval.py`。
4. **色板**：仍然只能从大面积纯色块标定；`docs/色卡-显示.jpg` 是暖光下拍的
   抖动图，反推只会得到偏白偏土的值（同 10-31 的教训）。

### 踩坑：调色函数的返回值是 sRGB，不是线性

`epd_preview.tone_map()` 返回**sRGB 0..1**；而 `algo_fs_gm_lin()` /
`ok_gamut_map_lin()` 吃的是**线性**。这一轮先写成
`algo_fs_gm_lin(tone_map(...))`，等于把 sRGB 当线性用，整体提亮一大截，
渲染出来的浅蓝/青全部变纯白、草绿变亮橙——第一版结论全错。
正确写法是 `algo_fs_gm_lin(srgb_to_lin(tone_map(...)))`（`epd_preview.py`
自己的 main() 就是这么做的，见该文件 490 行）。写测量脚本时先对照 `main()`
的数据流，别凭函数名猜。
